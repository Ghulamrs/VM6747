# TMS6747 — a C6000 code-generation target for the VM6747 line

**Goal.** Teach `cc1i`, `cxx1i`, and `shci` to emit for a third architecture:
the TI **TMS320C6747** (C674x, C6000-family VLIW DSP). Output is **C6000
assembly text only** (`-S`); there is no assembler for it on the machines this
builds on, so there is no assemble/link step and no on-box run test.

## Emission strategy
- **Serial**: one instruction per execute packet (no `||`). No functional-unit
  assignment to get wrong; VLIW scheduling is a later, optional concern.
- **Delay slots filled with `NOP`**: `B` → `NOP 5`. Correct, not fast.
- **Stack-machine over a primary register**, the same shape the x86 and arm64
  backends use (evaluate into `A4`, spill to the stack for the other operand).
- **EABI**: result in `A4` (`A5:A4` for 64-bit), return address `B3`, stack
  pointer `B15`, no leading underscore on names. `long` and pointers 32-bit,
  `long long` 64-bit, `double`/`long double` 64-bit.

## Milestones
1. **Target stood up + integer-constant returns** — DONE (cc1i, cxx1i).
2. **Locals, integer expressions, assignments, if/while/for, return values** —
   DONE (cc1i, cxx1i). Also unary `- ~ ! & *`, postfix `++`/`--`, and
   short-circuit `&&`/`||`.
3. **Parameters and calls (the ABI)**, globals, strings, casts, wider types.
4. The rest (structs, varargs, floats, division), then port to shci.

Each milestone grows the backend one shape at a time; anything past the
current milestone calls `unsupported()` and exits, exactly as the arm64
backend refused shapes it had not reached yet.

## The emulator: VM6747/Emulator, `vm6747.exe` (2026-09-13, `d754c99`)
An assembly-level C674x simulator with delay-slot timing and a native C
library, so the backend is **run, not just read**. `Compiler-Ci/tests/
tms6747.sh` compiles every corpus case with cc1i, runs it on vm6747, and
compares with clang's native run: **399 pass, 0 fail, 26 skipped** (the

the target: stdarg.h, float.h, limits.h, errno.h.

**C++ on the emulator (same day, Emulator `bc83033`, Compiler-Cppi
`ac998ba`..`89c6b2d`):** the C++ ABI runtime - `__dynamic_cast`, the
`__cxxabiv1` typeinfo vtables, `_Znwm`/`_ZdlPv`, `__cxa_guard_*`,

`Compiler-Cppi/tests/tms6747.sh`: **173 pass, 0 fail, 89 skipped for

**The Windows box is in the loop (Emulator `641f269`):** `msvc/build.cmd`
builds vm6747.exe with cl (-W4 -WX); `tests/windows.sh` relays the sources
by tar+scp (no remote, by the rules), builds on the box, runs every .s the

572 identical**. Two host differences were made the emulator's own: NaN is
printed and produced canonically (Windows wrote -nan(ind)), and /tmp maps

What the emulator proves is *internal* consistency: the code the backend
emits does what the C program means, under the conventions the backend and
the emulator share. The open questions below are about whether those
conventions are TI's; they stand until a TI toolchain checks them.

## Exceptions - TI's tables, since 2026-09-14 night
cxx1i lowers throw/catch to the Itanium runtime calls
(`__cxa_allocate_exception`, `__cxa_throw`, `__cxa_begin_catch`,
`__cxa_end_catch`, `__cxa_rethrow`, `_Unwind_Resume`), which TI's
rts6740_elf_eh.lib defines, and the backend writes TI's own tables
(lib/src/tdeh_pr_common.cpp, tdeh_pr_c6000.cpp, read in
scratchpad/ti/tdeh): every function has a `.c6xabi.exidx` entry - its
address and the compact unwind word inline, or `$EXIDX_EXTAB` naming a
table when there are handlers - and a function with handlers has
`.c6xabi.extab:f`, `__c6xabi_extab$f`: the unwind word, then one scope
descriptor per handler per call-site range the Walker collected, then 0:

    .half  $EXTAB_SCOPE(end) - $EXTAB_SCOPE(begin) [+ 1 for a catch]
    .half  $EXTAB_SCOPE(begin) - $EXTAB_SCOPE(f) + 2
    .ulong $EXTAB_LP(pad$sN)                 the trampoline for selector N
    .ulong $EXTAB_RTTI(_ZTI..) | 0xffffffff  a catch's type, or catch (...)

The range is [begin+2, begin+2+len), so a return address at `end` is in
and one at `begin` is not. TI's personality reads a function's descriptors
in order and lands the pad with the exception in A4 and nothing else, so a
row's selectors become trampolines - `pad$s3: MVK 3, B4; B pad; NOP 5` -
and the pad stores A4 and B4 in the parser's slots, puts B15 back to the
frame's base, and dispatches as it always did. A row's catches come first,
one per type in its chain (the enclosing tries' types after its own), and
its cleanup last, so phase 2 lands once on the barrier's pad, whose
selector walks the chain of pads the parser built; a cleanup landing (a
throw nothing here catches) runs the pad with selector 0, which ends in
`_Unwind_Resume` - TI's entry, which carries on with the descriptor after
the cleanup's. Over each cleanup pad's own code - the parser's unwinding
blocks, marked `Block::unwindCleanup` - a catch-and-terminate scope
(`.ulong 0; .ulong 0xfffffffe`) as cl6x writes one, so a destructor that
throws while an exception unwinds terminates (tests/cases/
dtor-throws-unwinding.cpp, this target only: the host tables have no such
region, registered in tests/open).

The emulator's runtime reads the same tables the same way
(Runtime::throwFrom/unwindTo): phase one scans each frame's catch
descriptors for the first whose range holds the return address and whose
type takes the exception - the same type or a public base, found by walking
the thrown object, which gives the adjusted pointer `__cxa_begin_catch`
returns - remembering the frame and the descriptor as the barrier, and
terminates with nothing unwound when none does; phase two scans again,
landing on each cleanup whose range holds the return address (A15 the
frame's, B15 as the throwing call left it, A4 the exception, B3 the pad)
and on the barrier's descriptor, and `_Unwind_Resume` continues the scan
after the cleanup that landed. Frames are walked through the index entries
(Runtime::callerOf). Not restored while unwinding: A10-B12 (this line's
code keeps nothing live in them across a call). The fundamental types'
typeinfo (`_ZTIi`, `_ZTIPKc` ...) are the runtime's. Checked against cl6x
on scratchpad/ti/eh.cpp: the same descriptors in the same order for the
three-handler try, our extra cleanup rows for the handler bodies, and the
program runs on the emulator; 281/281 C++ cases, 748 assembled and 739
linked by TI's tools.

**TI-hosted exceptions, step 1 of 3 (2026-09-14, night): the frame is
TI's, and every function has an exception index entry.** TI's unwinder
(lib/src/tdeh_pr_c6000.cpp, read in scratchpad/ti/tdeh) restores a frame
from the second word of its `.c6xabi.exidx` entry: for personality 3 the
word holds the return register, a bitmask of the registers saved, and the
SP increment - `0x7f` meaning SP := A15 - and then pops the registers a
word each downward from the restored SP in one fixed order: A15, B15-B10,
B3, A14-A10. So the frame was relaid to fit: A15 now points at the
caller's B15 word (the ABI's, the callee's to use; every call in this line
already reserved it), the caller's A15 is stored there, and the other
saved registers sit below it in that order - B12, B10, B3, A12, A10 when
the body loads the argument registers, B3 alone otherwise - in a 24-byte
area whatever is saved, so a local's address (`A15 - 24 - offset`) does not
wait on what the body turns out to call. The prologue is `STW A15,*B15; MV
B15,A15; STW B3,*-A15(4)...; SUB B15,24+frame,B15`; the epilogue reloads,
`MV A15,B15`, `LDW *A15,A15`. Each function ends with its entry, `.ulong
$EXIDX_FUNC(f)` and the inline word (`0x83ff0207` for A15+B3 with SP :=
A15; `0x83000007` for a frameless leaf), and the unit `.global`s and
`.symdepend`s `__c6xabi_unwind_cpp_pr3`, as cl6x does. shci's frame keeps
no A15: its saved registers sit at the top of a fixed frame, its word
carries the frame's size in doublewords as TI's own compact entries do, and
the word at its B15 is now the callee's (it held B3, which the relaid
runtime overwrote - 58 of 94 failed until it moved). cc1i, cxx1i and shci
all emit the entries; the emulator's assembler takes `.c6xabi.exidx`,
`.ulong`/`.uhalf`, `$EXIDX_FUNC()` and the other `$EXTAB_*()` operators as
the symbol's address, and `.symdepend`; and its own unwinder now finds each
frame's return address *through the index* (Runtime::callerOf), so a wrong
bitmask or a register out of order is a wrong return address and a failed
case - the walk is TI's reading of our word, not a private convention.
Verified: 403/280/94 on the emulator, cc1i's fingerprint re-recorded (427
tms6747 digests moved, no host one), 747 assembled and 738 linked by TI's
tools, lnk6x defining `__TI_UNWIND_TABLE_START/END` over the table and
pulling in `__c6xabi_unwind_cpp_pr3` and `_Unwind_RaiseException`.
**Steps 2 and 3 followed the same night** - the handler rows became TI's
scope descriptors and trampolines, the emulator reads them by TI's rules,
and cl6x's tables for eh.cpp agree - see "Exceptions" above; `.vm6747.eh`
is gone. The catch-and-terminate scope followed on 2026-09-15. What would make it "runs on silicon" rather than "TI's tools take
it and the emulator agrees with our reading of TI's source": a board, or a
simulator; neither is here.

## Open questions to confirm as the ISA fills in
- **Plain `char` signedness** on TI C6000 — set to *signed* to match the other
  backends here; verify against TI's convention before it matters.
- **`long` width** — set to 32-bit (EABI). The legacy COFF ABI's 40-bit `long`
  is deliberately not emitted.
- **Stack arguments at SP+4** — the emitted convention is that the word at
  the caller's SP is reserved for the callee (TI prologues store B3 there
  with `*SP--(8)`) and the first stack argument sits one word above it.
  Confirm against `cl6x` output for a call with more than ten arguments.
- **Symbol characters** — labels and static-local names carry dots
  (`L.return.f`, `L.str.0`, `next.n`). TI's documented symbol alphabet is
  alphanumerics, `$` and `_`; if the assembler rejects dots, respell them
  once, everywhere (`L$return$f`), rather than case by case.
- **Variadic calls** — emitted with the last named argument on the stack
  beside the variadic ones, as TI's `va_start` (which steps from `&parmN`)
  requires. Confirm against `cl6x` output for a `printf` call.
- **Division helpers** — named `__c6xabi_divi`, `__c6xabi_divu`,
  `__c6xabi_remi`, `__c6xabi_remu` (the EABI names; the COFF ABI's were
  `__divi` etc.), and called as ordinary functions. The EABI lets them
  clobber less than a function may, which is not relied on; only the names
  and the A4/B4 -> A4 convention need confirming against the RTS.
- **Structs** — passed by the address of a copy and returned through A3
  regardless of size, the COFF-era convention. The EABI may return small
  structs (8 bytes or less) in A4/A5 instead; confirm against `cl6x` for a
  function returning a two-int struct before linking with TI-compiled code.
- **Floating-point delay slots** — NOP counts are taken from the C674x
  instruction latencies as remembered (ADDSP/SUBSP/MPYSP 4 cycles, ADDDP/
  SUBDP 7, MPYDP 10, compares 2, INTSP 4, INTDP 5, SPTRUNC/DPTRUNC 4, SPDP/
  DPSP 2); check each against the C674x CPU reference before trusting a
  result that a too-short NOP would corrupt. Too many NOPs is only slow.
- **Shift counts of 32 or more** — the 64-bit splice relies on a single-word
  SHL/SHRU/SHR by a register count of 32 giving 0 (or the sign): the C6000
  takes the low 6 bits of the count. Confirm in the CPU reference; if only
  5 bits count, the splice needs a special case at 0.
- **64-bit helper names** — `__c6xabi_divlli`, `divull`, `remlli`,
  `remull`, `fixflli`, `fixdlli`, `fixfull`, `fixdull`, `fltllif`, `fltllid`,
  `fltullf`, `fltulld`, from memory of the EABI's helper table; check the
  spelling against the RTS before linking.
- **`.weak` as a weak definition** — TI's ELF assembler is expected to give a
  symbol that is both defined in the module and named in `.weak` the
  STB_WEAK binding, and the linker to keep one of several. If its `.weak`
  turns out to mean only a weak *reference*, inline definitions need
  another spelling (a section per symbol with `.clink`, as cl6x does).
- **Verification** — there is no C6000 oracle on these machines (the family
  checks backends differentially against clang/gcc/cl, none of which targets
  C6000). Until TI's `cl6x`/`asm6x` is available somewhere, correctness leans
  on hand-written expected-output tests.
